# 企业统一待办平台后续功能开发路线图

## 1. 当前基线

当前仓库已经具备可运行的工程底座：

- Vue 3 + Vite + Pinia 前端预览应用；
- NestJS API、Swagger、统一参数校验、异常格式和请求日志；
- Prisma + PostgreSQL 数据层；
- Redis 与 BullMQ 基础连接；
- `Department`、`User`、`Task` 初始数据模型；
- 本地 Mock 用户、JWT 登录、会话恢复与退出；
- API、PostgreSQL、Redis 健康检查；
- 类型检查、构建、单元测试和 API 端到端测试命令。

当前任务列表仍是静态预览数据，用户、部门、待办、集成和同步模块尚未提供业务 CRUD。

## 2. 产品目标

平台最终需要把多个业务系统中的待办统一汇聚到一个工作台，解决以下问题：

1. 员工不必反复打开多个系统查找待办；
2. 外部待办能够可靠地进入统一任务模型；
3. 用户可以查看、筛选、处理和追踪自己有权限访问的任务；
4. 平台能够识别重复事件、处理失败重试，并保留同步审计记录；
5. 新接入一个业务系统时，不需要修改统一待办核心逻辑。

## 3. 开发原则

- 每个迭代都必须形成可以演示、测试和回滚的完整增量；
- 先完成本地业务闭环，再接入真实第三方系统；
- 第三方字段不得直接侵入统一任务核心模型；
- 外部系统凭证不得出现在日志、接口响应或 Git 仓库中；
- 所有列表接口必须考虑鉴权、分页、筛选和稳定排序；
- 所有同步写入必须具备幂等键和可追踪的执行记录；
- 每个接口同步补充 Swagger、单元测试和端到端测试。

## 4. 推荐迭代顺序

### 迭代一：组织与用户只读能力

**目标：** 建立后续待办授权、负责人选择和组织筛选所需的身份基础。

**功能范围：**

- `GET /departments`：返回部门树或扁平列表；
- `GET /departments/:id`：部门详情；
- `GET /departments/:id/users`：部门成员；
- `GET /users`：用户分页与关键词查询；
- `GET /users/:id`：用户详情；
- 接口使用 JWT 保护；
- Swagger、服务单元测试和 API 端到端测试。

**验收标准：**

- 登录用户能够查询种子部门和用户；
- 非法 UUID 返回 400，不存在的资源返回 404；
- 未登录访问返回标准化 401；
- 列表排序稳定，分页参数有明确上限；
- 不提供组织和用户写入接口。

### 迭代二：本地待办最小闭环

**目标：** 用真实数据库数据替换前端静态预览，形成第一个可用业务闭环。

**功能范围：**

- `POST /tasks`：创建本地待办；
- `GET /tasks`：查询当前用户待办，支持状态、关键词、截止时间和分页筛选；
- `GET /tasks/:id`：待办详情；
- `PATCH /tasks/:id/status`：状态流转；
- `PATCH /tasks/:id`：修改标题、描述、负责人和截止时间；
- 前端待办列表、空状态、加载状态和错误状态；
- 前端创建待办、查看详情和更新状态；
- DTO、共享契约、Swagger 和完整测试。

**建议补充的数据约束：**

- 状态继续使用 `PENDING | IN_PROGRESS | COMPLETED`；
- 本地创建的任务固定 `source = LOCAL`；
- 任务必须至少有标题和负责人；
- 默认只允许负责人查看和操作自己的任务；
- 列表使用 `createdAt DESC, id DESC` 保证稳定排序。

**验收标准：**

- 页面刷新后任务仍然存在；
- 不同模拟用户只能看到自己的任务；
- 创建、查询、详情和状态更新完成端到端闭环；
- API 对越权访问返回 403 或资源不可见策略定义的 404；
- 前端不再展示硬编码任务。

### 迭代三：待办流转与审计

**目标：** 从简单任务列表升级为适合企业使用的可追踪流程。

**功能范围：**

- 任务创建人、处理人、来源部门；
- 转派、退回、取消和重新打开；
- 操作备注；
- `TaskEvent` 或 `TaskHistory` 审计表；
- 任务时间线；
- 逾期标记与按截止时间排序；
- 基础角色：普通用户、部门管理员、平台管理员。

**验收标准：**

- 每次状态变化、转派和关键字段修改均有审计记录；
- 非法状态迁移被服务层拒绝；
- 用户只能执行角色允许的操作；
- 时间线不泄露无权限用户信息。

### 迭代四：集成配置与第一个连接器

**目标：** 建立可扩展的连接器边界，并以一个真实系统验证设计。

**推荐首个连接器：** 钉钉。当前项目设计已经预留钉钉认证和企业 SaaS 集成方向，先接一个系统更容易验证统一模型，避免同时适配多个平台造成过度抽象。

**功能范围：**

- `Integration` 配置模型；
- 连接器接口：鉴权、拉取待办、读取详情、确认处理结果；
- 凭证加密存储与脱敏展示；
- 管理端连接测试；
- 外部用户与本地用户映射；
- 外部任务到统一 `Task` 的字段映射；
- 连接器契约测试和 Mock Server 测试。

**验收标准：**

- 凭证不会以明文出现在 API、日志和 Git 中；
- 连接失败能返回可理解但不泄密的错误；
- 同一外部任务拥有稳定的 `source + externalId` 标识；
- 连接器实现可以被替换为测试桩。

### 迭代五：可靠同步队列

**目标：** 使用 BullMQ 把同步过程从请求链路中解耦，并保证失败可恢复。

**功能范围：**

- 定时增量拉取；
- 手动触发同步；
- BullMQ producer、worker 和队列事件监听；
- `SyncRun`、`SyncItem` 或等价同步记录；
- 幂等写入；
- 指数退避重试；
- 死信记录和人工重放；
- 同步状态查询接口与管理页面。

**验收标准：**

- 重复投递不会创建重复待办；
- 单条失败不会阻断整个批次；
- 每次同步能够查看开始时间、结束时间、成功数、失败数和错误摘要；
- worker 重启后未完成任务能够继续处理。

### 迭代六：通知、搜索与工作台体验

**目标：** 提高统一待办平台的实际使用效率。

**功能范围：**

- 我的待办、已完成、我发起的、部门待办；
- 组合筛选、全文关键词和保存筛选条件；
- 临期与逾期提醒；
- 站内通知，随后再按需要扩展钉钉或邮件通知；
- 批量完成和批量转派；
- 首页统计卡片和趋势图；
- 移动端适配与无障碍检查。

### 迭代七：生产化与运营能力

**目标：** 让系统满足真实企业环境的安全、稳定和运维要求。

**功能范围：**

- 真实单点登录和令牌刷新策略；
- 多租户或企业隔离策略；
- RBAC 与数据权限；
- 审计日志查询和导出；
- 数据库备份与恢复演练；
- 指标、日志、链路追踪和告警；
- 限流、幂等请求、防重放和安全响应头；
- CI/CD、容器镜像和分环境配置；
- 性能、并发、故障恢复和安全测试。

## 5. 下一步建议

下一次开发应只启动“迭代一：组织与用户只读能力”。它范围小、依赖清晰，并且能验证当前 JWT、Prisma、共享契约、Swagger 和前端状态管理是否适合作为长期基础。

完成迭代一后，再为“本地待办最小闭环”单独编写设计和实施计划。不要在同一个变更中同时加入组织查询、任务 CRUD、钉钉连接和队列同步。
